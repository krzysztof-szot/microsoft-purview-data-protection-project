# Investigate and withdraw the lab DLP policy

1. **Take the report.** Capture UTC time, fixture ID, user alias, site, action attempted, policy-tip text if shown, and effective guest access. Use the original authenticated guest session or a clean profile signed in as that same guest.
2. **Check the control.** Retest the neutral file with the same guest. If both files fail, verify invitation redemption, link validity, sharing settings and permissions before attributing the denial to DLP.
3. **Find the matching signal.** In DLP alerts or eligible Activity Explorer views, filter by a bounded UTC window, SharePoint, fixture and policy. In Audit, look up related actor/file operations where available. Record rule, SIT or label, actor and event timestamps as emitted by each source. Service or scanner activity can have a different actor and time from the guest action. [Activity Explorer](https://learn.microsoft.com/en-us/purview/data-classification-activity-explorer) · [Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search)
4. **Correlate the records.** Link the rule outcome and the access observation by fixture and test window. Record the separate IDs locally where visible. Mark a result `PENDING` while telemetry is still being processed. If a test cannot start because a view or feature is unavailable, use `NOT_RUN` and give the reason.
5. **Withdraw the lab control.** Record the selected site and current mode. Disable only `BFL SharePoint External Access`. After propagation, retest both original file links with the same guest. Check remaining policies or separate access controls if recovery fails. Record the observed effect before revoking lab sharing.
6. **Publish the record.** Redact tenant names, domains, users, guest links, identifiers and unrelated content. Keep supporting context under the case ID. Write the redacted evidence paths to the matrix and capture the UTC timeline in the [capstone](capstone.md).
